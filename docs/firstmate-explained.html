Firstmate, explained

What it does, how it does it, where it earns its complexity, and how to get most of the same value from Claude Code's own built-in features.

Source: this repository at branch claude/first-mate-architecture-analysis-ep0h01 · AGENTS.md, README.md, docs/architecture.md, bin/, .claude/settings.json · 30 Sep 2026
Executive summary

One agent you talk to. A crew of agents that does the work.

Firstmate is an "agent distro", not an app. It is a folder containing a very long instruction file (AGENTS.md), a set of skills, and about 190 bash scripts. When you start Claude Code (or Codex, Pi, Grok, etc.) inside that folder, the agent reads the instructions and becomes a supervisor. You describe work in chat; it writes a written brief, starts a separate coding agent for each task in its own terminal tab and its own git worktree, watches them all without spending tokens, and comes back to you only with finished pull requests, investigation reports, or decisions it needs you to make.

What it's for

Running 3 to 20 coding tasks in parallel across several repos without juggling terminals, while keeping a human in charge of every merge.

How it works

Everything is files on disk plus terminal sessions. A bash loop watches those files and wakes the supervisor only when something needs attention. Restarting loses nothing.

Native alternative

Claude Code now covers roughly 70% of the core with built-in parts: subagents, worktree isolation, background agents, hooks, a task list, PR subscriptions, and scheduled wakeups. A five-file setup is shown in section 7.

Recommendation

For a single developer on Claude Code, build the native version. Adopt Firstmate only if you need many different agent tools, workers you can watch and type into, multi-machine fleets, or hard restart-proofing.

01

What Firstmate is, in plain terms

Running one AI coding agent is easy. Running four at once is not: you end up with a row of terminal tabs, copying context between them, forgetting which one had the failing test, and approving things half-read.

Firstmate reorganises this like a ship. You are the captain. You speak to one agent only, the first mate. The first mate never edits your code. It hires crewmates (other agent sessions), gives each written instructions and a private copy of the repository, checks on them, and reports back in plain language. For large setups, it can also delegate whole areas of work to second mates: persistent supervisors with their own separate home folder, on the same machine or another one over SSH.

There is nothing to install beyond the repo. The "product" is the instructions plus the scripts that make those instructions reliable. The agent tool you already use provides the intelligence; Firstmate provides the job description, the memory and the safety rails.

02

How one task travels from request to merge

Every request goes through the same fixed sequence. Each step is owned by one script, and each script refuses to proceed if a required fact is missing (for example, the delivery mode) rather than guessing.

Three details that make this work

  • The brief is a contract. fm-brief.sh generates it with fixed sections: Captain's intent (your words, verbatim, used as acceptance criteria), Firstmate spec (only what the ask needs), plus a fixed safety block: stop if you are in the main checkout, which status words to use, what "done" means for this delivery mode.
  • Status is a one-line protocol. Workers append lines like working: …, needs-decision: …, blocked: …, paused: …, done: PR <url>, failed: …. That tiny vocabulary is what lets a bash script, not an LLM, decide whether anything needs attention.
  • Delivery mode is chosen per task. no-mistakes runs a full automated review/fix/test pipeline before the PR; direct-PR opens a PR straight away; local-only leaves a clean branch for an approved fast-forward merge. A separate yolo flag decides whether green work may be merged without asking.
03

The supervision engine: waiting without paying for it

The hardest problem Firstmate solves is not starting agents. It is noticing when one of them needs help, without the supervisor burning tokens by polling in a loop, and without ever ending a turn "blind" while work is still running.

The answer is a plain bash loop, bin/fm-watch.sh. It sleeps, then checks cheap signals: new status lines, whether a worker's terminal output changed (by hashing it), whether a PR merged, whether a timer fired. It classifies each change in bash. Routine noise is absorbed. Anything actionable is written to a durable queue on disk and only then does the loop wake the LLM.

Four kinds of wake exist, and each has a fixed handling rule:

WakeMeansFirst mate does
signalA worker wrote a status line that matters (done, blocked, needs a decision).Reads it, checks current state, acts or asks you.
staleA worker's screen stopped changing and it isn't provably busy.Inspects the terminal; runs the stuck-worker recovery playbook.
checkA registered poll reported something (PR merged, inbox note, public mention).Acts on the result: record the merge, clean up, reply.
heartbeatPeriodic timer.Reviews the whole fleet and backlog; starts queued work whose blockers cleared.

Wakes are acknowledged only after they are handled. If the supervisor crashes mid-turn, the same wakes are presented again on restart. This "durable queue plus acknowledge after handling" pattern is the core reliability idea, and it is why so much of the code exists.

04

Memory lives on disk, not in the conversation

Firstmate treats the chat transcript as disposable. Anything that must survive goes into a file, so you can kill the session at any time and the next one rebuilds the picture from disk and from the live terminal tabs. At startup bin/fm-session-start.sh takes a lock (so two supervisors can't fight), drains the wake queue, and prints one digest of everything below.

05

The safety rails

The five hard rules in priority order, as written in AGENTS.md. Most of the scripts exist to enforce these mechanically so the model cannot talk itself out of them.

  1. Never write to a project. The supervisor reads; only workers change code, and only inside their own worktree. fm-spawn.sh refuses to start a worker in the primary checkout.
  2. Never merge without the captain's word. A per-project yolo setting is the only standing exception, and it never allows merging a red PR.
  3. Never tear down unlanded work. fm-teardown.sh checks that commits actually landed and refuses otherwise.
  4. Workers never address the captain. All communication is routed through the first mate.
  5. Report outcomes faithfully. Failures are reported plainly with evidence.

There are also softer rules about how to talk to you: lead with outcomes, not mechanics; never paste raw status lines; always include the full PR URL when asking for a merge; stay silent while nothing has changed.

A minimal "first mate" in five files

These are complete and usable as written. They reproduce the core loop: triage, brief, isolated parallel workers, PR delivery, human-gated merge, and a startup digest.

CLAUDE.md (orchestrator section)
## Orchestrator role
You are the orchestrator for this workspace. You do not edit project code yourself.

Hard rules, in priority order:
1. Never edit files in the main checkout. All code changes happen in a subagent
   launched with isolation "worktree".
2. Never run `gh pr merge` unless the user has said "merge" for that exact PR in
   the current conversation.
3. Never delete a worktree or branch whose commits are not on origin.
4. Report outcomes plainly, with the PR URL, never raw logs.

Lifecycle for every request:
- Classify: **ship** (produces a PR) or **scout** (produces docs/reports/<slug>.md).
- Add it to the task list (TaskCreate) and to BACKLOG.md.
- Write a brief: the user's words verbatim under "Intent", then only the build
  steps the ask requires under "Spec", and what is out of scope.
- Launch with the Agent tool: subagent_type ship|scout, isolation "worktree",
  run_in_background true. Independent tasks launch in the same message.
- While workers run, stay silent. On each completion notice: update the task,
  tell the user the outcome + PR URL, and subscribe to PR activity if available.
- A worker that returns NEEDS-DECISION: decide if the answer follows from the
  user's stated intent; otherwise ask the user one concise question, then resume
  the worker with SendMessage.
.claude/agents/ship.md
---
name: ship
description: Implements one scoped change in an isolated worktree and opens a PR. Use for any authorized code change.
tools: Read, Edit, Write, Bash, Grep, Glob
model: sonnet
---
You are a ship worker. You receive a brief with "Intent" and "Spec".

1. Confirm you are in a git worktree, not the main checkout:
   `git rev-parse --git-common-dir` must differ from `git rev-parse --git-dir`.
   If not, stop and return "BLOCKED: not isolated".
2. Create branch `ship/<short-slug>` from the fresh default branch.
3. Implement only what Intent and Spec require. Add or update tests.
4. Run the project's lint, build, and test commands. Fix failures.
5. Commit, push, and open a PR with `gh pr create --fill`.
6. Wait for CI with `gh pr checks --watch`. Fix red checks up to two times.
7. Return exactly one line:
   DONE: PR <url> checks green
   | NEEDS-DECISION: <question with options>
   | BLOCKED: <what stopped you>
   | FAILED: <evidence>
Never merge. Never address the user directly.
.claude/agents/scout.md
---
name: scout
description: Investigates, reproduces, or audits and writes a report. Never pushes code.
tools: Read, Bash, Grep, Glob, Write, WebFetch
model: opus
---
Investigate the question in your brief. Reproduce before concluding; separate
cause from correlation; note disconfirming evidence.
Write the report to docs/reports/<slug>.md with: Question, Findings (with
evidence), Options, Recommendation, Open decisions for the user.
Return: "REPORT: docs/reports/<slug>.md" plus a three-line summary.
Do not commit, push, or open a PR.
.claude/settings.json
{
  "permissions": {
    "ask":  ["Bash(gh pr merge:*)"],
    "deny": ["Bash(git push --force:*)", "Bash(git worktree remove --force:*)"]
  },
  "hooks": {
    "SessionStart": [
      { "hooks": [ { "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/digest.sh" } ] }
    ],
    "PreToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [ { "type": "command",
          "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/no-main-edits.sh" } ] }
    ]
  }
}
.claude/hooks/digest.sh and no-main-edits.sh
#!/usr/bin/env bash
# digest.sh: printed into context at session start (the "fleet digest")
set -euo pipefail
cd "$CLAUDE_PROJECT_DIR"
echo "## Backlog";      sed -n '1,60p' BACKLOG.md 2>/dev/null || echo "(none)"
echo "## Worktrees";    git worktree list
echo "## My open PRs";  gh pr list --author @me --json number,title,url,statusCheckRollup \
                          --jq '.[] | "\(.url)  \(.title)"' 2>/dev/null || echo "(gh unavailable)"

#!/usr/bin/env bash
# no-main-edits.sh: block Edit/Write in the primary checkout (hard rule 1)
set -euo pipefail
input=$(cat)
path=$(jq -r '.tool_input.file_path // empty' <<<"$input")
[[ -z "$path" ]] && exit 0
main=$(git -C "$CLAUDE_PROJECT_DIR" rev-parse --show-toplevel)
case "$path" in
  "$main"/BACKLOG.md|"$main"/docs/reports/*|"$main"/CLAUDE.md) exit 0 ;;
  "$main"/.claude/worktrees/*) exit 0 ;;
  "$main"/*) echo "Orchestrator may not edit project files; delegate to a ship agent." >&2; exit 2 ;;
esac

Note on the hook. Subagents launched with worktree isolation work in a separate directory, so the path check lets them through while blocking the main session. Adjust the worktree prefix to wherever your Claude Code version places agent worktrees (check git worktree list after one run).

Optional upgrades, in order of value

  • PR follow-through. In a cloud session, subscribe_pr_activity delivers CI failures and review comments as wakes. Locally, /loop 15m check my open PRs and report merged or red ones does the same with a small token cost per tick.
  • Heavier validation. Replace step 4 of the ship agent with a Workflow that runs review, test, and fix agents in a pipeline. That is the native analogue of the no-mistakes gate.
  • Second mates. For a separate domain, start a separate session (create_session in the cloud, or another terminal in a different repo) with its own CLAUDE.md. Coordinate via SendMessage or GitHub issues rather than shared files.
  • Away mode. A CronCreate or Routine that fires "summarize what finished, list decisions waiting" at your return time, plus PushNotification for blockers.
  • Durability. Have the ship agent commit and push early (draft PR on first commit). If the session dies, the branch and PR survive and a new session's SessionStart digest picks them up.

Which one to use

Native Claude Code if you work alone, use only Claude models, and are fine with workers living inside one session. You get the core pattern (one orchestrator, isolated parallel workers, human-gated merges, zero-cost waiting) in about 150 lines of config you fully understand.

Firstmate if you need any of: workers in real terminal tabs you can jump into; mixing Codex, Gemini, Pi and Claude with quota-aware routing; in-flight workers that survive a supervisor crash; persistent sub-supervisors on other machines; or public-mention handling. Those are exactly the areas where most of its 90k lines of bash are spent.

A middle path: copy Firstmate's ideas, not its code. Its most portable ideas are the verbatim-intent brief, the one-line status vocabulary, per-task delivery mode, "acknowledge a wake only after handling it", and the rule that the orchestrator never edits code. All five fit in the native setup above.
